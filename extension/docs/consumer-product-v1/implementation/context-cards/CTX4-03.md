## Owner and data contract

The existing Thought owner retains Topic identity, lifecycle, stable order,
Sections, Entries, Input bindings and all content. Context stores only explicit
local choices over those IDs. It does not add a catalog, taxonomy, copied Topic
body, provider, permission, DB version or object store.

The existing strict `context-cards:v1` row cannot accept Topic selection fields
without changing its prior Item/receipt contract. The minimum separate owner is
one `context-topic-access:v1` preference row in existing `meta`: version, row
revision and unique choices containing Topic ID, enabled, selection revision
and the reviewed identity binding. It is bounded to 4096 choices and 4 MiB.
Missing state reads as default off without a write. Unknown versions, extra
fields, malformed bindings and duplicate IDs refuse without rewriting the row.
Names, bodies, summaries, Profile instructions and receipt results are not
stored in the preference row.

`context-topic-access-policy.js` evaluates complete trusted facts while retaining
`externalAllowed: false`. A choice binds Topic ID, creation identity, restore
epoch, current layout/removal identity and the current structural operation's
durable receipt sequence/digest. Raw negative redirect ancestry restricts; it
never transfers an allow. Same-ID rename and ordinary membership additions do
not manufacture a new identity. Merge, removal/restoration and repeated layout
Undo/redo cannot renew an old choice implicitly.

`context-topic-scope.js` reads the actual current same-Entry memberships,
Sections, Inputs, all legacy permission profiles and exact operation receipts.
It validates count/page completeness and current identity/source/filter/binding
facts. A different Entry sharing an Input remains a distinct idea; direct
Input/source restrictions still apply to every consumed Input. Missing,
malformed, stale or over-budget facts return no partial snapshot or binding.
The bounds are 4096 references, 100-row pages, 131072 accounted reads, 8192
selected-field hashes and 8 MiB of transient UTF-8 hash input. These are explicit
refusal bounds, not a 20/50/144-topic taxonomy or truncation permission.

Selected-field freshness follows the canonical Entry reader. One material read
transaction captures bounded transient hash inputs. Existing `hashText` runs
after that transaction closes, followed by a metadata-only consent, restore,
filter/foundation and authority fence. No WebCrypto await holds a live IDB
transaction. Transient text is cleared before return; only body-free facts leave
the producer. The token proves freshness, not caller authentication.

## Explicit changes and failure behavior

`ContextTopicAccessService` owns the directory, strict local preference changes
and outcomes. Directory rows use current canonical Topic metadata and the
existing stable creation/ID order, including retained stale choices. No Root
index initialization, excerpt read or second durable directory is needed.
Cursor authority, complete traversal and hard budgets are checked. Unselected
Topics have no positive policy result; enabling one runs the complete producer.

Enable requests carry the displayed binding and selection revision as
preconditions. A strict write rechecks current consent/restore epoch, exact
authority, raw Topic/receipt binding and CAS before saving the trusted binding
and body-free `context-topic:` receipt atomically. Receipts use namespace
`context-topic-access` and the exact validated request digest. No normalization
changes retry identity. The existing receipt write advances read authority;
there is no new global generation owner.

The trusted worker reserves in-flight attempts before hashing or scope reads.
Repeated identical calls share one attempt; different payloads with that ID
refuse. Outcome remains unknown while an attempt can still write. A historical
acknowledgment confirms only the saved choice, not present read permission.
UI retry retains the exact operation, Topic, binding and intent. An impossible
successor revision, wrong Topic or invalid no-op acknowledgment is not accepted.

Disable can turn off a stale saved choice without renewing its binding. Global
or Input pause retains choices. Stronger legacy deny/never, Entry/Input/Section
exclusions, source/filter eligibility and unknown identity facts continue to
block effective access. Independent Info/Rules/Now Items remain separate.

The real My Inputs surface uses the existing approved capsules and shared shell.
It traverses to the true end, preserves stable ordering/focus, distinguishes
saved selection from current eligibility, and uses existing route/leave guards.
Pending unknown writes block leave; loading replies cannot remount a superseded
page. Home reports selected-choice counts, not an externally readable count. Its
bounded preview uses at most three current stable-bound selected Topic labels
from the existing qualified label owner, plus the retained remainder. Stale
identities stay counted without displaying their old name; hidden source-derived
labels use the existing masked replacement. Global/category pause preserves the
local preview. No names are copied into the preference row.
Missing/corrupt Topic preferences do not replace unknown counts with zero or
prevent independent Item pages from reading their own valid state.

## Restore, purge and compatibility

The row is nonportable. Existing-file replacement preserves it but rotates the
existing restore epoch, making prior enabled bindings ineffective. Disjoint
import cannot create a local choice or replace an existing binding. The new
local receipt namespace and reserved prefix are explicitly rejected by the
existing Backup admission boundary; prior namespace/schema/version rules stay
unchanged. No export feature is reopened.

Body-free toggles add no editor recovery kind. Existing Source purge admission,
its B-02 refusal and all Source/Input/Thought invariants remain owned by the
original services. The worker uses its existing extension-page and consent
gates; host/content, wrong-origin and wrong-extension callers cannot use these
commands. The Context local-change notification does not start provider work.
