# Original Repository terminal read fences

## Narrow source mechanism

`registerRepositoryFinalReadFence(repository, scope, {plan, isCurrent})` registers only against the original Repository's exact live write scope. A forged, copied, foreign, readonly or completed scope cannot register. Registrations accumulate; later registrations cannot replace prior checks. Once finalization starts, late registration is a sticky failure. In the terminal phase, original put/delete/clear, derived writes and out-of-plan Repository reads abort even if a callback catches their rejection.

The private original scope record also requires its `tx` own data property to retain the exact original transaction and its repository to retain the original database. Closed read specs accept only plain/null-prototype objects with own data properties and the known operation keys; getters, inherited operation fields and symbol additions are rejected without acquiring their values.

All existing navigation, semantic and backup-generation finalizers run first. Each strict plan is a synchronous generator yielding only exact original `get` or metadata `count` operations. There is no unbounded `all`, arbitrary callback await, async generator or thenable checker in that closed segment. Before and after each read, every registered currentness predicate must return exactly true. All predicates run again after all plans and immediately before awaiting the original transaction completion. Any violation aborts the original transaction. The domain owner supplies its own original frozen facts and charges its original shared budget; registration grants no body access or provider authority.

This mechanism protects original Repository methods and the closed read driver. It is a trusted source-owner contract, not a sandbox for arbitrary malicious comparators: the existing public native `scope.tx` remains available, and a separately retained native transaction can call `objectStore(...).put()` outside these method guards. The actual Promotion owner plan uses only yielded point/count requests and its frozen captured facts; it does not invoke native writes. No general native-transaction API redesign is included.

A separate, still-active Section Promotion integration candidate (not included in this four-path Repository checkpoint) freezes selected Input/Source facts before its mutation, retains its pre-put exact intent/Entry graph, and registers their terminal comparison. Its only anticipated root change is the original Repository's precise backup-generation increment. Point keys plus complete original member counts fence graph and restrictive-metadata additions without scanning final-stage bodies. Original legal Topic/Entry/Placement/history writes remain valid; finalizer changes are not refreshed into the expected baseline.

Legacy direct identity processing still has an asynchronous resolver without a synchronous source-owned permission capability. Its optional compatibility recheck occurs before the closed read-plan segment and is explicitly **not native atomic revocation assurance for an arbitrarily delayed resolver**. Strict production promotion remains denied until a separate original identity-processing capability is available; field qualification cannot replace that permission. A constructor callback by itself does not establish production identity or a deployed paid bridge.
