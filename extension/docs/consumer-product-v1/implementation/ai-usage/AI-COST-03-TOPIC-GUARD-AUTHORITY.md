# Topic guard: exact identity uses and closed final restore check

## Limited source integration

This successor connects the independently branded Topic identity authority to the original `TopicProcessingGuard`. It implements the independent processing/current-state boundary required by AI_USAGE_PLAN §5 and AI_USAGE_ARCHITECTURE §§5, 9–10; it does not install a production issuer or complete the paid Section Promotion/confirmation lifecycle. The separately frozen 92-case authority slice and the Next/R3 594-case repair keep their original identities.

The original resolver still receives the exact `personal-topic-identity` request. An authority-bearing response must supply a genuine same-store, same-live-original-transaction capability from `TopicProcessingAuthority`; the guard compares its original epoch, ordered Input/Topic IDs and captured restore epoch. A body-free restore-row read uses the same original branded request ledger, and the genuine capability is rechecked after that read. No Topic labels, Input/Entry fields, Context bodies, new grant or model-supplied authority are acquired here. Independent field qualification remains necessary for the original strict identity reader; a real retrieval test composes both authorities rather than substituting one for the other.

The guard privately records **every** actual processing use for each original transaction, including legacy calls. Legacy direct APIs retain their original asynchronous resolver behavior. Any missing/legacy use prevents a strict terminal claim; a later branded call cannot upgrade the earlier use. Copied, foreign-store, previous-readonly, completed, released, wrong-scope and wrong-epoch capabilities fail. Original prototype reader facades can resolve their exact underlying transaction; a copied own `tx` property cannot borrow its brand.

`assertProcessingCurrent(transaction)` synchronously checks the complete original use collection, genuine issuer currentness/deadlines, transaction identity and original ledger. It does not itself perform an IndexedDB restore read. `registerProcessingFinalFence(transaction)` freezes that collection and registers the original Repository closed final-read plan. After all original finalizers, this plan executes one exact `meta/recovery-restore-epoch` IDB get and compares the value to every captured use. The request ledger charges the control read without resetting any limit. Repository performs its existing true-only synchronous currentness checks before/after reads and at completion. No async issuer, permission refresh, new baseline, crypto or external work enters the terminal plan.

After registration, another processing call is rejected before invoking an issuer. Replacing the public resolver cannot replace the private collection. Revoking the earlier of two individually valid registered uses fails the final transaction even if its last use remains valid. A second registered fence cannot conceal revocation after the first fence's read. The new `topicProcessingAuthorityWorkBudget` accessor exposes the existing source-only branded ledger only after validating the genuine use; it grants no fields.
