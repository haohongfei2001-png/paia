## Original contract and the manual-create boundary

`AI_USAGE_PLAN.md` §5 and `AI_USAGE_ARCHITECTURE.md` §§3–5 require relevant restoration/corrections, original-domain validation, protected human Items, complete authorized evidence, and separate exact Topic/Context acknowledgement. The current CTX4 plan retains those original incremental-maintenance obligations.

A newly created manual Item is source-free human content. Its successful human put receipt proves that write; it does not prove completed interpretation. The existing `ContextMaintenanceService` rejects a manual target. Its explicit NO_CHANGE operation requires an eligible unprotected automatic Item and actual evidence. Therefore this slice does **not** manufacture a local manual-create Context ACK, borrow unrelated Input provenance, or reinterpret manual content as an automatic Item. Manual creation/change/restoration interpretation and Topic interpretation of changed Context remain pending. Their eventual mapper must have a truthful original-domain result and independently authorized selected material; a new product rule is not inferred here.

The permitted finite closure is human restoration of an existing protected automatic Item whose **entire original plain body-only Input lineage is still current**. It uses the existing purpose-scoped Context fields, actual admitted mapper/provider route, and original protected-Item result. No new command, canonical Item field, human/maintenance receipt shape, provider, account, permission, default route or external grant is added.

## Original delete/restore causal authority

The original `ContextCardsService.change` owner now prepares the existing ephemeral correction capability for automatic-Item delete and restore as well as put. Manual Items return no such capability.

- An original delete transaction records a body-free `contextRemoval` witness in its existing known semantic-delta descriptor. The full Item semantic digest binds identity, card, human body/section/order, creation identity, lifecycle/deletedBy and complete original maintenance provenance. Revision, update time, protected/user-edited state and successful exact human receipt are checked separately.
- The original restore preparer requires the exact adjacent deletion receipt and this witness, the same epoch, Item, removed revision and deletion operation, and an unchanged full removed preimage. The original transaction rechecks both the actual deletion receipt and known witness after asynchronous hashing before recording the restore witness.
- The existing `contextEdit` descriptor gains a `restore` kind and the deletion receipt ID/digest plus removed-semantic digest. This is a narrow extension of rebuildable local scheduling metadata, not a canonical schema migration or a grant. A hash or copied receipt alone is insufficient.
- Old deletions lacking the original removal witness stay pending after restoration. There is no guessed historical migration or receipt reconstruction. A new restore cannot consume an older nonadjacent deletion or another Item/Source's witness.

The active restored Item is hashed against both its current semantic witness and the reconstructed exact removed semantics. Existing independent Context-field and full Input processing checks, exclusion/Source tombstone checks, Topic/membership restrictions and complete original lineage hashing remain. The deletion and restore receipts join the captured Item/Input/Source/Topic/legacy snapshot, including the final original Context/ACK transaction fence after its last asynchronous authority check.

## Truthful result and compatibility

The mapper still requires the original UPDATE request for this exact Item/revision/card/associations/evidence. Only the original Context transaction's `protected` result settles the **Context** unit with NO_CHANGE and zero effective result. The human Item is unchanged. Topic remains pending; explicit NO_CHANGE/REMOVE_CANDIDATE commands are not substituted. Duplicate restore receipts and completed handles do not create another provider attempt or ACK. A changed admitted route may reconsider only its old exact Context mapping DEFER, retaining job/attempt history.

The metadata extension does not change Backup or Sync. Backup's existing allowlist rejects both known/dirty AIU rows, and its receipt validator rejects both human Context receipts. The existing Sync current-snapshot owner is manual-only and rejects automatic Items; manual delete/restore journal chains retain their original codec and owner. Restored metadata cannot activate processing or external access: both current authorities remain independently required, and epoch replacement invalidates old witnesses. No Sync feature work was introduced.
