# AI-COST-03 restored Input-bound Entry Context mapping

## Bounded local behavior

This slice extends the already supported restored Input-bound Entry Topic route to its Context facet. Only the original user restore journal with exact lifecycle field mask and current Entry revision qualifies. Independent authored Entries, title/note changes, other non-Input kinds and arbitrary retry reasons remain unsupported. Original formation material qualification supplies the actual current Working Input and Entry body; processing permission includes the exact Entry revision and body field even when only Context coverage remains. Duplicate facet references do not duplicate Entry material or Input evidence.

The adapter receives explicit Entry-to-Input metadata but must return the original Entry coverage key. Exact evidence closure and the original Context owner validate eligible current Input/Topic membership, lineage, processing and human protection. Entry mapping is checked before and after the original Context transaction callback; Item publication and exact subset ACK roll back together on drift or storage failure. No new content store, provider, scheduler, public route, permission or financial authority is installed.

A configured mapper can reconsider only exact original CONTEXT_MAPPING_UNAVAILABLE rows with current qualifying Entry evidence. The new Context reconsideration option requires a current route version different from the original job, in the original archival transaction. In this combined capability pass the same version fence covers Topic rows too, preventing a same-route subset from creating a new job indirectly. Default cleanup and the prior standalone Topic API remain unchanged. A new capability route is supplied by the existing private host; no automatic version churn or cancelled-job revival is introduced. Old receipts/jobs and possibly billed attempts stay intact. Explicitly closing a dispatched partial job remains necessary before admitting a different remaining-scope job.
