## Metadata selection, scope and payload

`ai-usage/maintenance-existing-context.js` stores opaque per-child handles in an ephemeral WeakMap. `selectMaintenanceExistingContext` runs inside the original bounded metadata read before the independent processing resolver. It projects only Item identity/revision/card/lifecycle/protection, original association/provenance metadata and selected-field descriptors. It never acquires Item body, section or temporal text at this stage. Manual, human-edited, protected and removed Items are excluded. Invalidated automatic Items retain their old provenance and invalidation history for genuine novelty checks.

Every required historical Input and selected field, authored/bound Entry proof, and selected human Topic/Section membership closure must already fit the child's processing scope. No new Input is inferred from old evidence. Same-name Topics, surviving ambient associations, same-source Input permission and whole-Topic access do not authorize Item fields. `captureMaintenanceExistingContext` requires exact independently granted `existingContextItems` descriptors plus the same current Input/Entry/structural scope before material reads. A metadata-only complete Topic graph guard prevents the original whole-Topic reader from acquiring an unselected sibling or an ungranted Entry body.

The provider receives only `{itemRef,itemId,revision,card,origin,protected,userEdited,lifecycle,body,section}` and, when stored, the original temporal projection `{temporal,temporalStatus}`. Item ID is the existing response target; no new wire target is invented. Original associations, source identities, epoch, old/current provenance, and owner snapshots remain local. Current evidence uses the actual selected current text and original identity/removal binding, while the old Item baseline remains exact. A changed current Input is not incorrectly compared to its historical digest.

The summary is `{version:1,coverage:'selected_processing_scope',selectedItems,omittedItems,complete}`. It describes only candidates relevant to the selected child. Omitted, unsupported, ungranted or overbudget Items do not become a false whole-profile comparison or automatic NO_CHANGE claim. The source response mapper must truthfully DEFER operations without a sent, matched, qualified baseline.

## Original bounds, cleanup and final fences

There is no arbitrary eight-Item cap. Selection reuses `CONTEXT_READ_LIMITS.page = 20`, union lineage `CONTEXT_LINEAGE_LIMITS.inputs = 16`, Topic union 8, Source union 128, canonical row limit 512, and original request/content allowances. Each overflow omits the complete Item at metadata selection. The nine-Topic test creates all nine Topics/Inputs/Items through original owners; the Source-union129 test is explicitly a schema-valid adversarial historical-row check, not fabricated qualified Source evidence. Complete Items are omitted rather than truncated; array brackets and commas count. Zero remaining allowance acquires no Input, Source or Item body. Session integration reserves the exact existing request envelope before passing the remaining allowances; its final payload validator still owns the original full ceilings.

Helper metadata/current-material reads and the single deduplicated original lineage capture share one branded `createContextScopeWorkBudget` with its unchanged 131072 reads, 8192 hash fields and 8 MiB hash ceiling. The only additional `context-item-lineage.js` interface is optional `workBudget` in `captureContextEvidence`; omitted options retain original behavior. Unbranded, different-database/signal or already exhausted budgets are rejected before a new material phase. There is no per-Item allowance reset. Retained selected Source/Working data also has an original 8 MiB bound.

Abort and failure release retained text and original lineage handles. Explicit release, session child completion and disposal invalidate the opaque handle. Repeated capture only rechecks the frozen selection; it does not reacquire a new baseline or grant.

When a relevant baseline exists, the first independent grant freezes every already-selected child Input field and its necessary Source, within max20 / Source128 / 8 MiB and the same shared budget. This anticipates a lawful same-child Topic publication adding one of those already-selected Inputs to the old Topic; it does not expand old Item provenance, currentEvidence or NO_CHANGE coverage. Exact selected Item and Source/Working facts, removal/restore epoch, restrictions, original Topic graph and selected Entry/structural interpretation are rechecked through settlement. An actual Now expiry crossing invalidates the sent temporal interpretation; an UPDATE with no new time evidence clears its previous deadline through the original owner. REMOVE_CANDIDATE still requires active automatic unprotected unedited exact revision, original associations and complete old lineage. NO_CHANGE covers only the actual checked provenance subset. The helper does not produce a domain receipt or ACK.

A metadata selection with no candidates, or a captured empty baseline, may tolerate unrelated aggregate root changes while retaining epoch, gate and grant checks. A nonempty baseline requires the exact original root and graph, advanced only by original-owner branded, private expected-publication capabilities. Original Topic and Context publication tokens must form an exact before/after authority chain. Their pre-write expected metadata is applied to the frozen old graph; no live post-ACK snapshot is adopted and no arbitrary extra membership/provenance is accepted. A first, still-unread body capture after an earlier grant refusal may consume the strict original-owner publication chain for its effective authority; original metadata/revision, selected scope, grant and `h.admission` remain unchanged. Repeated capture never adopts live replacements. Selected Item replacement is separately limited to the original Context owner's immutable exact expected target. Partial/derived newly created Entry bodies do not gain permission through a publication token; the helper retains the original independent Entry-field guard. Token creation/final-fence integration belongs to the original owner/session implementation, not this helper.
