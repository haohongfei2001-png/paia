## Proposed first coherent local implementation

The first usable internal consumer should be a private `LocalAssistSession` explicitly constructed by a trusted host controller and never registered in the production worker. It must exercise actual observe → explicit prepare/run → validated result → qualified delivery capability, including zero relevant dependencies. A lease-only adapter that nobody consumes is not completion.

1. New `background/assist-reply-lease.js` takes trusted sender/tab/probe and two independent consent owners. Default both OFF. It verifies extension identity, top frame, documentId, active nonincognito tab, exact ChatGPT conversation and actual current adapter metadata. Observation stores metadata only. Access and remote processing each have a revocation generation; configure/revoke synchronously invalidates before any await. Restart creates a fresh session; caller metadata cannot recreate a lease. No Settings or worker hook is added in this slice.
2. New `core/ai-usage/local-assist-session.js` owns bounded private handles, raw current snapshot, validated output and singleflight. Deliberate activation alone takes a snapshot after both consents and reply/Context qualification. Ordinary open/hover/observe never assembles or dispatches. Use real feature-owned dependency selection, not arbitrary caller profile text. The initial private caller can supply only a trusted selector capability, not authority DTOs. Selected Context still passes the actual Context read/semantic owners. No relevant Context means an empty canonical dependency list, not a fake row.
3. A separate Assist result obligation is necessary: proposed new persisted discriminator `ai_assist_result_v1`, one child and one opaque reply-result obligation, plus zero-to-100 real dependencies. It is NOT ordinary facet coverage and not a new canonical entity. Existing v1 plans, identity and coverage rules remain byte-for-byte. Exact metadata identity includes lease/binding, dependency signatures, contract/route versions and authority; never reply/output text or raw URL. The old generic Foundation must reject this kind before mutation. No optional field on ai_usage_v1 can provide that isolation.
4. A narrow Foundation completion path validates the private response and every exact dependency/current permission, then invokes one trusted feature committer and settles the reply-result obligation in one transaction. Final synchronous private-current fences must run after all authority and ACK awaits, as with the existing guarded session owner. Exceptions roll metadata/result publication back, retaining actual dispatch/unknown history. Private output is exposed only after successful COMMITTED readback; lost ACK retries the same identity without a second provider attempt. Restart/private output loss does not authorize redispatch.
5. New isolated content-side delivery owner uses actual current-reply observer plus existing composer adapter. Constructor-created delivery capabilities bind document, lease, result, action and operation ID; public text is never a candidate. Get/copy/insert first requalify after awaited probes, then consume mutation records and synchronously assert exact lease/consent/result generation at the actual composer mutation. IME/draft checks and no-send are the existing adapter's responsibility. Uncertain insertion cannot blindly repeat. No new visible surface or production RPC is enabled; native fixture explicitly constructs the private controller in its trusted isolated context.

External Chrome probes run before canonical IDB transactions. The in-transaction resolver checks a captured private capability synchronously plus actual same-transaction Context/authority; it must not await Chrome messaging inside IDB. A final synchronous lease-generation fence closes invalidation during canonical awaits. This is not atomicity across browser processes: delivery rechecks the live content owner immediately before mutation, and disappearance/uncertainty denies delivery.

## Response, bounds and retained data

One result DTO should contain either bounded suggestion text with explicit prerequisite/condition or DEFER; exact schema and concrete character/byte bounds must be approved before producer code. Existing AI Assist one-child, input/output and total payload limits remain unchanged. Text length is not a substitute for qualified provider token accounting. No tool calls or arbitrary insertion destinations. Unsupported/truncated/unknown responses are not useful results and cannot silently release usage reservations.

Reply and generated text exist only in private process memory and the intentional composer insertion/copy destination; no Archive, Context, backup, job, ordinary diagnostics or persistent cache. Bounded handle/result tables must recheck capacity after awaits. Ten activations of the same current semantic reply/dependency identity share one flight/result; all generations are still rechecked at each use. Irrelevant Context text edits do not evict an authorized result; relevant edits/revocation do. Consent or reply A→B→A never revives an old execution handle.

## Review closure: exact local response and resource contract

The following are proposed strict internal format bounds, not a claim that the canonical token ceiling can be inferred from text length. Version 1 response admits exactly one of:

- `{version:1,kind:'SUGGESTION',text,condition}`: `text` is trimmed, nonempty, at most 120 Unicode scalar values and 480 UTF-8 bytes; `condition` is a string, empty when unconditional, otherwise trimmed, at most 120 scalars / 480 bytes. No choices array, confidence, raw evidence, action or arbitrary extra keys. The single text is the insertion payload; the condition remains visible delivery metadata and cannot be silently discarded by a consumer. Bound 120 reuses the existing local Next candidate size as a conservative presentation compatibility limit; it is not an assertion that generated Assist is a Next candidate.
- `{version:1,kind:'DEFER',reason}`: reason is exactly one of `INSUFFICIENT_CONTEXT`, `PREREQUISITE_UNMET`, `UNSAFE_REQUEST`, `NO_USEFUL_SUGGESTION`. No free text, replacement result or hidden retry instruction.

Both exact DTOs reject malformed/lone-surrogate strings, unexpected keys, non-plain objects, extra results and trailing non-JSON output. Serialized UTF-8 response ceiling is 2,048 bytes, checked before JSON parse; no truncation to make an oversized response valid. Text is data, never a tool instruction or permission. Condition-bearing results require a consumer that exposes the condition before insertion; otherwise delivery is unavailable. The first local batch may validate semantics only to the extent of explicit owner safety checks; it does not claim production utility/safety calibration.

The existing reply adapter outer ceiling (32,768 scalars / 131,072 bytes / 256 blocks) is unchanged. Assist takes only the exact completed current reply; its narrower assembly rejects, rather than slices, a reply above 4,096 scalars or 8,192 bytes. Relevant Context plus any explicitly qualified already-sent user message share 4,096 UTF-8 bytes; initial implementation omits the optional user message if no existing qualified owner is integrated. Final serialized provider payload, including instructions, schema, reply, Context and Foundation usage metadata, is limited to 16,384 UTF-8 bytes immediately before execute. This byte cap alone never authorizes paid work. ARCH section 10 still requires actual qualified tokenizer preflight for **all** payload parts ≤4,000 input tokens and an enforceable ≤600 billable output-token cap (including reasoning/API headroom), one child. Unknown tokenizer/route/financial authority leaves production unavailable. Local fixture responses are not a way to certify those gates.

Private tables are per controller: at most 8 live leases, 8 prepared handles and 8 result/DEFER slots; at most 2 running interactive jobs remains subject to Foundation's broader admission contract. No unbounded secondary key map. Entries expire after 5 minutes monotonic elapsed time from creation; clock rollback/unknown clock invalidates instead of extending. Reply/document/session/consent revocation or dispose invalidates immediately. Capacity checks occur both before awaited work and at final publication. Eviction of an undispatched entry is safe; an attempted job's opaque durable identity remains the no-redispatch authority even if its private output expires. Pending executions are not evicted to bypass limits; new requests refuse RESOURCE_LIMIT until capacity is available.

DEFER is a completed evaluation for that exact live lease/dependency identity, stored privately like a result after actual settlement; ten clicks reuse it, not ten calls. Only a genuinely changed qualified input/lease or authorized policy may make another logical evaluation eligible, still subject to attempt quotas. Malformed output/failed/unknown responses are not DEFER and do not receive useful-result accounting. After process loss the durable settled/unknown identity prevents redispatch; output is unavailable, not reconstructed from logs. The new obligation settlement must distinguish valid DEFER from effective suggestion while retaining actual usage; no financial refund is inferred.

Private candidate text can exist during validation but is not reachable through `result()`/delivery until the Foundation transaction resolves successfully and a current post-commit read confirms the same COMMITTED job/child/receipt. Abort leaves no published slot. Revocation between transaction completion and private publication denies publication. Lost ACK retries current durable identity using retained private output, never calls execute again; dispose destroys pending private publication capability.

### Final review: semantic identity and frozen closure

Private execution lease identity and durable semantic evaluation identity are distinct. A stable opaque session/document reply-cycle identity plus completed reply revision, exact relevant dependency signatures, contract/route version and independent consent epochs identifies the evaluation. TTL, eviction, handle replacement, ordinary reopen and a newly allocated leaseId do not change that identity. The new-kind job identity must use the semantic evaluation key, while every operation separately validates the current private execution lease. A settled/unknown evaluation with lost private output returns unavailable and cannot rerun. On a cold restart without the original trusted session/reply observation there is no automatic evaluation-key reconstruction and no processing of historical replies. A genuinely new observed reply cycle or changed qualified evidence can be a new evaluation; consent renewal does not automatically trigger execution, and old ABA handles remain invalid. The new bound owner must compare the returned job's semantic key and active lease rather than weaken legacy Assist binding equality globally.
