## Compatibility decision requiring approval

Use the same `meta` aiPresentation identity and revision owner, with a **structurally distinct, explicitly versioned derivative envelope**. Proposed envelope version2 stores `projection` (the existing eight readable fields) and `manifest` together, plus existing revision/protection/candidate lifecycle metadata. It omits old top-level readable fields, so the frozen old isStoredAIPresentation cannot silently accept a new partial projection. A new explicit candidate version3 binds the complete base-manifest digest, replacement manifest/projection digest, field choices and source scope. Do not repurpose old candidate version1/2 or add unvalidated keys to their proposals.

This is a derivative row-format evolution, not a new IndexedDB store or second authoritative Archive/Topic. The projection is deterministically derived from the same manifest version; it cannot be independently written. Public status/edit UI still receives the existing eight-field projection and existing field-level adoption controls. No new chunk renderer or block-level controls are introduced.

Legacy schema0/1 rows and candidate1/2 keep their current decoder, readability, human protection and recovery paths. They have no inferred literal-span manifest and are never automatically relabeled. A legacy row can enter v2 only through an explicit, fully validated recomputation/adoption; otherwise it remains legacy. A cold oversized legacy Topic may defer honestly.

Required compatibility owners cannot be omitted: ai-contract, ai-candidate, ai-presentation-migration, ai-draft, metadata retirement, typed AI history/restore and backup-service validation/fence reconstruction. Migration must recognize the new envelope rather than downgrade it to schema0. Purge must preserve only legitimate human fields and clear generated provenance correctly. Backup must use the new explicit decoder and producer-version gate; an old backup reader must reject unsupported data. Supporting arbitrary old binaries mutating a new database in place is not implied by a schema number. Frozen old read/candidate/import tests must prove the supported fail-closed boundaries. Coordinator owns app-version admission; this author does not alter it unilaterally.

## Manifest and delta rules

The manifest contains ordered stable derivative block IDs, exact field/list-position mapping, accepted generation/style/profile identity, and per-block current Entry support: Entry revision, dependency revision, exact provenance/Input/source eligibility fingerprint, actual Section/placement identity and order, and relevant chronology. It stores no second source body. Original text uses current Entry UTF-16 spans validated at grapheme boundaries; the accepted projection stores the already-validated derivative bytes. A span records its exact Entry revision and cannot be replayed at the same offset against a newer body to silently rewrite saved reading. After revision changes, preserve accepted bytes only as permitted by the original stale/readability owner, otherwise refuse reading or recompute; never dynamically substitute new source text into an old projection. generated balanced/concise text is the existing derivative content, with explicit supporting refs and no inferred verbatim fidelity. Separators for scalar-field composition are explicit bounded local formatting, never invented provider evidence.

Total retained manifest refs and transmitted job refs are different bounds. Propose an explicit v2 metadata ceiling of256 KiB (the existing cache metadata budget) and at most1024 distinct Entry refs/blocks. This is a proposed versioned safety bound requiring review, not a changed v1 limit or a special case for200. The v2 complete manifest/projection uses an independent explicit decoder: its aggregate refs must never be passed through a relaxed v1 validator or old public decoder. Each transmitted child response retains the original <=100-ref bound; an internal v2 assembly decoder combines qualified child references with retained local blocks. The public eight-field projection is produced only after that whole v2 envelope passes its own qualification. The eight-field text/list lengths remain unchanged. If the faithful projection does not fit, defer; do not truncate, summarize Original to fit, or invent a new reader. Each response replacement and each physical request remains within existing content/output limits.

Delta compares exact current support, including provenance changes even if displayed body text is equal. A block is reusable only when all its evidence and placement/Section/chronology conditions still match. Shared-support changes invalidate every dependent block. Added Entries are mapped to their actual Section/order; moves/deletes must not be mistaken for unchanged text. Unchanged blocks stay local and retain their IDs/text byte-for-byte.

Neighbors are not a fixed count added to every request. They are the directly adjacent retained block boundaries required to insert or replace a block inside the same actual Section/field mapping; record the reason and exact support for every sent neighbor. Do not cross Section boundaries or send the entire prior presentation. Pure appends to an empty or closed boundary may require no neighbor. Nonlocal summaries or blocks depending on broad evidence cannot be patched from five bodies merely to meet a token target: expand to their true dependency closure within bounds or defer that field with honest pending scope.

A response may replace only the exact planned block IDs and declared insert positions. It cannot alter untouched blocks, create durable Sections, widen source refs, claim checked coverage for neighbors not actually processed, or replace human-protected output. Output must include complete planned closure; omitted/duplicate/conflicting block IDs or refs reject the whole proposed patch.

## Protection, partial adoption and state ownership

Keep existing field-level human ownership. A human-edited field invalidates automatic block reuse for that field; preserve its exact text and existing recovery behavior. Do not split a protected field into supposedly unprotected fragments as a workaround. The provider can receive only explicitly allowed relevant evidence, never protected draft text by default.

Existing adoption remains explicit per field. Adopted fields receive their new complete block mapping; kept fields retain the prior mapping/text/protection. Mixed manifests must represent actual per-field provenance, not one falsely uniform generation stamp. Full exact-cache qualification requires complete coherent accepted coverage and no protected/manual/mixed pending work; partial adoption does not earn a full cacheBinding. Unaccepted/kept work cannot silently advance whole-Topic checkpoints. Generated blocks with revoked/purged evidence stop being readable immediately through the existing eligibility owner; legally retained human text continues through its existing recovery path.

Candidate creation must not replace the saved reading projection. Failed, partial, unknown or oversized output leaves the previously readable saved work available under current eligibility. Any mutation/restore/permission/style/generation change while a child is outstanding invalidates the prepared scope. No retry can remint a possibly billable attempt. A disposed session with a lost private response remains unavailable, even when the durable attempt says RESPONSE_RECORDED.

## Smallest useful vertical batch and four-child follow-up

**First batch:** versioned envelope/manifest plus actual single-child delta assembly, candidate/adoption/history/status. Keep the existing <=100 Foundation job and per-request maxInputs/bytes intact. The manifest may cover200+ retained Entries while only five added Entries and necessary local boundaries enter one actual request. If the delta does not fit one child, explicitly defer without dispatch; do not present this first batch as complete up-to-four support.

Prove the 200+5 workload without raw manifest injection: generate/adopt a small real v2 Topic, then grow it in successive real explicit bounded edits/refreshes until200 Entries are represented. Add five real Entries and call the same LocalOrganizeSession path. Check the actual provider payload contains exactly the five affected Entries plus justified boundary support, no retained bodies; all untouched blocks/projection text/IDs remain identical. This models a grown Topic with a valid existing cache, not cold full205 generation. Use additional 47+3 or similar sizes to rule out hard-coded200 behavior.

This is the minimum meaningful delivery because it fixes the actual full-Topic preflight and persists usable source spans through adoption. It is materially larger than a small adapter: all row-format owners above need one author and independent review. If that scope cannot be allocated atomically, do not split out a dead manifest helper and call it delivered.

**Second bounded batch:** 2–4 children with aggregate preflight and one final transactional publication. Preserve the original Foundation API; add a narrow explicit Organize closure method only after a reviewed diff. It must require all planned child receipts to be RESPONSE_RECORDED/valid, bind private validated outputs to exact job/child coverage, recheck full current authority, write the final domain candidate once, and settle all exact child coverage/receipts in the same IDB transaction. Refactor common settlement checks rather than copying or weakening them. Sequential calls to current commitFacet are insufficient to claim atomic multi-child publication. Until this exists, no partial candidate or successful coverage ACK may escape a failed multi-child closure. The canonical ceiling remains four; five must reject before any provider call. This follow-up is required before claiming complete canonical multi-child recomputation.
