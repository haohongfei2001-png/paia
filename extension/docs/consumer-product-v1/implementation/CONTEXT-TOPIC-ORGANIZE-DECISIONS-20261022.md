## 1. Cross-source relevance and old-evidence authorization

**Already present:** `selectMaintenanceExistingContext` selects bounded metadata only when every old evidence member is within this child's independently selected scope. Existing material capture and Context publication owners then enforce field authority, exact lineage, revisions, Source validity and human protection. Same-child Topic success cannot grant a new Entry's Context fields. Independently valid Topic + ACK can commit atomically while unauthorized Context remains unread/unwritten/unacknowledged, without another paid request.

**Proposed first extension, only after approval:** shortlist old automatic Items through already permitted metadata and exact stable Topic/lineage identity; capture a fresh independent grant for the complete old evidence closure and precise Item fields before reading any old prose. Retain omission/pending when closure, relevance or permission is unknown. Carry exact old/new snapshots through the existing final owners and successful-facet ACK transaction; never turn missing coverage into NO_CHANGE or global completeness. All existing count/byte/time bounds and charging remain; do not introduce an unlimited scan, permission union or paid retry.

**Minimum decision:** dot supplies (a) the accepted relevance predicate and (b) the issuer/scope contract for old fields. The narrow proposed predicate is exact shared stable Topic identity plus complete permitted lineage. If this is insufficient, an explicit qualified relation is an alternative, but its relation types and provenance must be specified first. Topic-name similarity, same Source Project, implicit alias union and model guesses are not approved predicates. Specify old Input/Entry/Item fields, allowed Sources, expiry/revocation and incomplete-closure behavior; processing permission and external Context release permission stay separate. This proposal authorizes no reads in advance of that decision.

**Regression once approved:** relevant and irrelevant same-name Topics; foreign Source denial with zero body reads; incomplete old closure; late revocation/purge/human edit; old/current Item CAS; exact successful subset ACK; unchanged physical attempt/financial record; native abort rollback and honest omissions. Existing in-scope tests and owners are reused.

## 2. Generated candidate becomes the current AI reading version

**Already present:** original candidate validation and adoption/CAS in `core/organizer/ai-candidate.js` and `ai-presentation.js`, protected derivative fields, original body ownership, revisions/journal and saved-version readability. The current Topic plan retires Candidate/Compare/Adopt management UI. Ordinary reading toggles are local projection actions and cannot perform a durable adoption or another model call. Generation's full authorized Topic scope is not reduced to the visible Section/year.

**Recommended behavior for approval:** successful explicit generation may publish one fully validated new derivative reading version through the original owner only when its captured base and all affected unprotected fields are still current. Original Entry bodies, Section identities/membership and manual order remain unchanged. If a human field is protected/edited, generation is stale, or the active editor/IME has unresolved work, retain the lawful previous reading and saved result; do not partially replace human text or silently make a mixed version current. Reflow only through existing leave/editor guards, preserving Section/Entry anchors. No candidate inbox or retired control returns.

**Minimum decision:** choose whether the existing explicit generation action also authorizes making that successful version current, or whether a separate action in the approved current Section/version surface is required. For the latter, dot must identify that concrete approved entry and its wording/state behavior; a generic instruction to restore Adopt is insufficient. Also confirm the recommended all-or-nothing replacement on protected-field conflict, versus a specifically designed field-level partial version. Existing internal field-level capabilities do not themselves decide the product semantics. If publication is deferred, dot must define how the saved result is reachable within the approved surface; do not leave an apparently successful generation inaccessible.

**Regression once approved:** first version, replacing an unedited version, protected field conflict, revision change during generation, pending IME/save, closed or switched Section, Source removal/revocation, durable transaction abort, restoration of old readable versions and no extra provider attempt. UI/source/release acceptance is distinct from internal CAS tests and live semantic quality.

## 3. Automatic Topic lifecycle

**Already present:** hidden Topic candidate accumulation/admission and `TopicLifecycleService.change` for active/dormant, with original independent identity/field checks, expected revision, final transaction fences, locked human lifecycle and memory protections. PT-08 defines dormant reuse without cloning, hidden candidate expiry without Source/Input/authored-content deletion, and explicit-only restoration of removed Topics. These are not saved AI-presentation candidates.

**Recommended integration for approval:** consume an already admitted Maintenance opportunity, using qualified original activity metadata and a versioned deterministic policy; do not introduce a periodic scheduler, paid call or permission issuer. Compute a bounded proposed transition, then call the existing lifecycle owner with its original independent grant/CAS. Missing activity proof or authority means pending, not dormancy. Keep/pin, human locks, removed/merged state and Source validity veto automatic transitions; reactivation preserves stable identity and constraints.

**Minimum decision:** supply one policy version with candidate retention duration, evidence window, active-to-dormant inactivity threshold, permitted reactivation evidence, and the actual activity-event owner/issuer. Proposed activity evidence is durable substantive human editing or qualified semantic reuse; page opening, viewport rendering, year expansion, sorting and AI metadata writes do not create activity. Dot must approve those event categories and numerical values; none are invented here. If existing Maintenance opportunities are insufficient, a background trigger is a separate design/authorization decision, not an implicit implementation task.

**Regression once approved:** exact threshold boundaries/clock anomalies; keep/pin/locked Topic; missing activity history; removed/merged anti-resurrection; reactivation keeps identity and restrictions; candidate expiry preserves independent content; concurrent edit/CAS; bounded continuation; late revocation and native rollback. No blanket new lifecycle corpus or duplicate store.
