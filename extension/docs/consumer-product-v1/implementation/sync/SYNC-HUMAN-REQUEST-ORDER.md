The same issue affects original edit semantics: `Object.keys/entries(request.changes)` determines Entry history `fieldMask` order and Topic per-field allocation/clock order. A receiver must not infer that order from sorted wire keys or after values.

Proposed mandatory descriptor fields: `requestOrder: string[]`, `changeOrder: string[]`, `fieldRevisionOrder: string[]`, and `ownerRequestDigest: hash`. `requestOrder` is the complete unique ordered top-level key array of the actual original owner request, restricted to that named operation’s exact finite existing request key schema. It includes optional keys only when actually present and JSON-safe; undefined/non-JSON values are unsupported before writing. It must be an exact set match to received request keys, and is never guessed from alphabetical wire order. Producer records this original order before serialization.

`changeOrder` is the complete unique ordered edit-key array. Producer derives it from the original private planner request, **before canonical serialization**. `entry-edit` requires exactly the original present `changes` keys (`title`, `body`, `note`, `type`, `formation`, bounded five); ordinary `topic-edit` requires exactly original present `changes` keys (`name`, `summary`, `pinned`, bounded three); `topic-edit` with `renameOnly=true` requires `['name']` and its original `request.name`, without manufacturing a changes object for that different original owner. Every other kind requires `[]`. Missing, duplicate, unknown, swapped semantic order not matching original output, wrong-kind, incomplete or additional fields refuse. This is qualification metadata, not new authorization or editable fields.

The **wire qualification** digest is `hashText(canonical({request,requestOrder,changeOrder,fieldRevisionOrder,ownerRequestDigest}))`, using the existing canonical JSON helper. The **original owner receipt** digest remains exactly `hashText(JSON.stringify(originalRequest))`; no bound or unbound owner receipt/idempotence algorithm is changed. Producer emits `ownerRequestDigest` from that original preparation, and receiver reconstructs both top-level and edit key order before rerunning the exact original planner. It requires that planner's original operationReceipt.digest equal ownerRequestDigest (KeepSeparate has no receipt, so the reconstructed original request digest itself is checked). Members/descriptor use the separate wire qualification digest to bind the transport request, while canonical operationReceipt and duplicate detection retain the original owner digest. Both digests are checked before the final transaction. Different top-level or edit order under an existing original operation ID still follows the existing original owner's collision semantics; it cannot silently become a new receipt hash.

Receiver validates the required exact shape, declared key set and options, then reconstructs the exact top-level request and the ordinary edit's `changes` insertion order using only the declared existing keys and exact values. It does not reclassify events, change defaults, invent keys, infer values or reorder clocks. It reruns the same actual original planner and requires full canonical/history/result/allocation/mapping agreement. All validation/seals occur before the final original transaction. Changed `requestOrder`, `changeOrder` or `ownerRequestDigest` with recomputed cryptographic descriptor digest must still fail original planner equality or strict event exhaustion before any canonical/protocol mutation.
