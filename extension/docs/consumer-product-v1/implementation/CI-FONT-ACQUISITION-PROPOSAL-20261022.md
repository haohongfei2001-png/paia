## 建议：只缓存经当前签名索引核验的字体包字节

采用现有 GitHub 缓存机制的离线设计，缓存对象仅为两个既有包以及实际必要依赖的 `.deb` 文件。保留原 signed-source 配置、apt update、完整安装配置、fontconfig处理、`fc-list :lang=zh` 和三个原 `fc-match` 输出。不是缓存整个系统字体目录或浏览器 profile，也不改变包候选版本选择。

顺序如下，尚未接入任何 workflow：

1. 在当前 runner 上执行原签名索引刷新，读取当前原源的候选版本、架构、文件SHA256和依赖闭包。不得从缓存里的清单取得信任；索引签名链必须来自当前原 apt 配置。
2. 生成精确缓存键：Ubuntu image身份、发行版/架构、此策略版本、完整包版本及可信索引给出的文件哈希。无跨版本/跨架构宽泛回退键，不缓存 apt lists 或源配置。
3. **命中**：逐个校验缓存文件与当前可信索引哈希、包名/版本/架构及完整依赖集合一致。只有全部通过，才按原安装方式消费本地包；不跳过 dpkg/字体缓存生成和原字体检测。安装计划不得引入未核验的其他版本。
4. **未命中或缓存不完整/损坏/版本改变**：把该条目视为未命中，执行一次原来的 signed apt 获取/安装路径。若原路径失败，保留真实失败；不循环重试、不换源、不放宽校验。成功并核验后，可信工作流才可以保存这个精确缓存项。
5. **失效**：原源候选/哈希、依赖、Ubuntu image、架构、策略变化均产生新键。旧键只能按现有缓存保留策略自然淘汰；不自动清除其他项目缓存。fork/不可信 PR 写出的缓存不得作为信任来源，即使命中也必须按当前签名索引独立验真；保存权限与事件必须由 dot 在工作流审查中明确。

此方案主要避免重复的68.7MB下载；每个新runner仍执行安装和全部校验。冷启动十个分片可能同时未命中，不能承诺首轮就受益；不为预热而额外派发 CI，不新增全局准备job或凭据。既有源偶发变慢仍可能影响冷未命中路径。真实节省量尚未测量，不能以597秒历史值保证每轮收益。

## 为什么暂不采用更大的改动

直接检测字体“已安装”然后跳过 apt update，可能保留旧候选版本；缓存已展开字体目录可能绕过 dpkg/字体配置。删除 CJK 字体、使用相近字体、改源、增加18分钟预算、减少case或改变分片均超出最小提案。每个job当前只有一次字体安装，不能假称删掉同job重复步骤即可解决。
