## 已从本地源码确认的事实

- 当前适配器扫描普通聊天中已加载且已显示的用户消息，没有按消息发送年代排除旧消息。历史补录是现有且必须保留的产品行为。
- `core/store.js` 在新快照首次成功保存时写入 `capturedAt`；重复捕获同一来源与同内容不改该字段。源消息改动产生另一份快照，拥有自己的首次捕获时间。
- 记录目前没有 `sourceSentAt`、`firstObservedAt`、`timeSource`、`timeConfidence` 或稳定的 `conversationOrder`。
- `ui/archive.js` 当前按 `capturedAt` 排列时间线、分日期组。界面有“捕获于”的标识，但此排序不符合本次新增的“原始发送时间优先”要求。本轮保留运行行为，不能声称新时间线已经实现。
- 现有 `pageOrder` 只是一次扫描中已加载用户消息的序号。懒加载、分支、切换或不同加载窗口都可能改变它，不能直接重命名为完整聊天的绝对消息序号。

## 真实页面采样需要的安全诊断

下一步需要在用户桌面 Chrome 的实际对话上执行受限 DOM 诊断。当前 v0.1.2 不包含这项时间诊断：不能让用户从现有结构摘要中找不存在的字段。可在接通受限 Chrome DOM 访问后直接调查；也可在现有扩展中另加仅检查公开属性的诊断，然后由用户更新、在真实普通聊天采样并反馈安全摘要。两者都不要求用户手写代码，不修改记录模型。

诊断边界：

- 保持同意、暂停、普通聊天身份、可见 user role 与稳定 role ID 门禁。对编辑态、临时聊天或身份不明不探测；分别报告跳过计数。
- 仅检查 user role 自身、该消息的有限后代及有限祖先属性。祖先到 main 前停止，共享多个消息的容器不能视为单条消息发送时间来源；不扫描兄弟消息、侧栏、整页或 React 私有对象。
- time 元素只检查结构和公开属性；不读取其文本内容。检查 datetime、时间相关 data-*、title/aria-label 的明确机器格式、公开语义时间属性。未知 data-* 属性名称仅用于局部分类，不输出任意原始属性名或值。
- title/aria-label 可能含正文片段；只在页面内进行严格格式判定，判定后丢弃原值。禁止把字符串、HTML、时间值、消息 ID、URL、标题或异常原文带出页面、写日志、测试或 Git。
- 设明确的消息/节点/祖先层数上限，并输出 inspected、skipped、truncated。只有覆盖完整、未截断且样本非空时，才能回答“是否每条都有”；范围不足时必须标未知。

安全摘要建议只包含计数、布尔值和固定枚举：

| 类别 | 输出内容 |
| --- | --- |
| 覆盖 | 可见 user 数、合格数、实际探测数、具有候选元数据的消息数、跳过数、是否截断 |
| 来源 | TIME_DATETIME / DATETIME_ATTRIBUTE / DATA_TIME / TITLE_TIME / ARIA_LABEL_TIME / PUBLIC_SEMANTIC_TIME 等固定类别及消息计数 |
| 位置 | ROLE / DESCENDANT / LIMITED_ANCESTOR；涉及共享祖先的候选单独标为不可归属 |
| 格式 | 机器可解析数量、明确时区数量、缺少时区数量、格式歧义数量 |
| 精度 | DATE / MINUTE / SECOND / SUBSECOND / UNKNOWN 对应计数；精度不等于可信度 |
| 一致性 | 同消息多个候选是否冲突；刷新前后是否一致。比较在本地完成，不输出比较用的 ID 或时间值 |
| 完整性 | allMessagesHaveMetadata、allMessagesHaveParseableMetadata、completeCoverage；无法确定时用固定 UNKNOWN 状态 |

即使属性可解析，也不能立即当作原始发送时间：它可能是内容中引用的日期、编辑时间、渲染时间、聊天创建时间或更新时间。只有确定是单条已发送用户消息的发送事件、归属唯一、时间语义明确、精度/时区可解释，并通过旧消息刷新与实时新消息对照后，才进入具体提取设计。不能从 message ID 解码时间，也不能用当前时钟判断并补齐缺失年份、时区或精度。

## 候选数据模型（建议；未迁移、未实施）

| 字段 | 类型/建议值 | 含义 |
| --- | --- | --- |
| sourceSentAt | 可明确解释的 ISO 8601 时间或 null | 用户真正发送此消息的时间；未知保持 null，绝不以捕获/观察时间回填 |
| capturedAt | ISO 8601 时间 | 本地首次成功持久保存这份快照的时间，重复扫描不覆盖；用于审计和诊断 |
| timeSource | unknown / verified_dom / official_export | sourceSentAt 的证据来源；仅“发现可解析候选”仍为 unknown，不填 verified_dom |
| timeConfidence | unknown / confirmed | sourceSentAt 的可信度；精度另记，缺少证据不得填 confirmed |
| sourceTimePrecision | unknown / date / minute / second / subsecond | 来源本身的精度；不能用补零或默认本机时区伪装更高精度 |
| conversationOrder | number 或 null | 同一聊天/分支内经确认的稳定相对顺序；不能直接复制某次 pageOrder；缺乏连接关系时为 null |
| firstObservedAt | ISO 8601 时间或 null | 满足“持续观察中的新消息”证据时首次看到该消息的本地时间，不是服务器发送时间 |
| firstObservedConfidence | approximate 或 unknown | 为观察时间单独标注近似性，避免让 timeConfidence 被误解为发送时间已确认 |

顺序还需要记录其适用的聊天分支/已知片段及证据范围；无法判断两个加载片段先后时，不凭捕获先后补成完整聊天顺序。源消息编辑快照还需区分“原消息发送”与“修改时间”，本轮不设计自动覆盖规则。

历史补录的缺省情况：`sourceSentAt=null`、`timeSource=unknown`、`timeConfidence=unknown`；capturedAt 保留原首次保存时间。打开旧聊天、刷新、延迟渲染及懒加载第一次出现的节点不能仅因“第一次看到”就算实时新发送；没有可靠实时证据时 firstObservedAt 也不能被解释为近似发送时间。若未来需要记录所有节点的首次可见时间，应另标 loaded_history/unknown 观察类型。

官方数据导入仅列作后续可能的精确历史时间回填渠道，本轮不实现文件读取或导入。届时必须另行明确用户授权的文件范围、格式和稳定身份映射；不能按“相同正文”或捕获时间猜测匹配，也不能覆盖不可变原文。

## 时间线建议（未实施）

1. 有可信 sourceSentAt 的记录按该时间排序并显示发送时间；保留实际精度。不要把捕获日期用作发送日期分组。
2. sourceSentAt 相同、且属于同一聊天/分支时，用已确认 conversationOrder 排序。
3. sourceSentAt 未知的历史记录明确放入“发送时间未知”的分组，同聊天内按已确认的 conversationOrder 展示；不把它们放进捕获当天的发送时间线。不同聊天之间没有准确历史先后依据。
4. capturedAt 仅作同等证据下的最终稳定兜底，必要时再用记录 ID 打破相同键；不显示成发送时间。近似 firstObservedAt 如需展示，单独标“首次观察（近似）”，不写入 sourceSentAt。

不能简单写成“有两个 sourceSentAt 就比较时间，否则同聊天比较顺序，否则比较 capturedAt”的任意两条记录比较器：混合已知/未知时间可能产生不传递的比较结果。应先明确已知/未知分组，再采用组内一致的排序键。这个分组方案保留用户建议的证据优先级，同时诚实表达未知时间。
