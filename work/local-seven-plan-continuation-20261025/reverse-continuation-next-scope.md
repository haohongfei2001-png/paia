## Current conclusion

Keep the archive **HELD / NOT INTEGRATABLE**. I found no proven removable metered cost that establishes a complete reverse within the original 4096 references / 2 MiB / 30 seconds. The observed 7069-byte overshoot occurred during B's terminal transaction, before A's required terminal transaction; it is not the complete shortfall. No per-phase actual accounting or successful terminal/cold receipt exists. A durable counter alone also cannot make an oversized operation fit.

One genuinely redundant calculation is visible in `application-generation-selection.js:401`: `returnDigest` computes `controlPublicationEncoding(value)` to charge its bytes, then calls `controlPublicationDigest(value)`, whose implementation in `local-control-publication.js:28` encodes the same value again before `hashText`. Reusing the already validated encoding for the same hash is algebraically equivalent for these privately held plain values, with the same exception/identity/deadline checks retained. However, the current budget charges that encoding only once. This would save an unmeasured CPU traversal, not the recorded bytes/references; it cannot be offered as a solution or justify a positive rerun. A small isolated equivalence check would be ordinary future development, but was not performed here.

## Why full reads cannot simply be discounted

The six separately durable A/B phase CAS transactions and two pre-SDK full reads each observe a different cross-connection window. Their comparisons of actual rows against the retained expected cut are a different operation from reading the rows. The original owner identity, process-local `tail`, and prior write fence do not globally exclude another database connection. The A/B expected cuts are deliberately updated after each actual phase; an old table hash or reference identity is not a replacement for the current full CAS.

The initial retained-copy charge, structural hash traversal/encoding, page requests/results, active-generation preparation and finalizers are real work. `returnHashes` charges physical operands plus encoded bytes; `returnRequireRows` charges expected comparison operands in addition to IDB's returned rows. These are not a second accidental charge of the same operation. The implementation already removed a separate warm pre-read before its first full transaction and already reuses retained warm expected cuts in settlement. I found no further mechanically equivalent metered deletion without changing the work model or transaction protocol. This is a scoped source conclusion, not a mathematical proof that every possible redesign fails.

Current pre-SDK `requireReturnMinimumCompletionCapacity` counts only a necessary floor. It does not cover every active preparation, control read, receipt/marker operand, final read, page continuation, and late failure. It therefore cannot certify completion availability. It must not be renamed a sufficient reservation.

## Missing durable protocol

Current v2 marker has operation identity and before/after hashes but no authenticated cumulative spend, outstanding work lease, remaining deadline evidence or exact continuation owner. All accounting is in the live WeakMap ticket. Cold `continueReturn` correctly creates only a fresh readonly inspection and never writes, reissues SDK set or refunds the original operation. Its `before-observed` result cannot prove the SDK was never dispatched; `after-observed` is not a terminal receipt.

A viable durable same-task continuation would need all of the following, not merely a `remainingBytes` field:

1. One original operation/accounting owner, tied to both exact repository identities, original control revision/reservation, dataset, direction, before/after digest and protocol version. An original protected metadata record is needed; arbitrary caller DTOs must never mint the private IDB selection authority.
2. Monotonic cumulative consumed-or-reserved references and bytes. Reserve a bounded stage envelope durably **before** the stage's external/native work. A crash or lost reservation response leaves that lease spent/unknown, never available again. In-memory actual charges must stay within the envelope without double charging or refunding across a restart. The reserve/read/finalizer operations themselves need a finite included allowance; they cannot be exempt bookkeeping. Fixed-size counters and a fixed stage whitelist avoid recursive unbounded accounting.
3. One accounting home and exact native CAS revision for single-writer stage claims. Two mirrored counters are not cross-database atomic. A/B phase records need a verifiable operation/lease/revision chain to that home. Cross-connection contention, a half-written pair and lost native completion must preserve restriction, never infer a free slot.
4. A sufficient pre-SDK terminal upper bound for the **complete** fixed final path, including real native preparation/finalizers and failure bookkeeping. This requires either all mutable inputs bounded and exact original protection enforced, or refusing before SDK whenever the bound cannot be proved. Unlimited retry reserves are not permitted. Existing full-row validations remain mandatory.
5. Deadline continuity. The existing 30 seconds are elapsed work lifetime, not a fresh slice on every process. The live monotonic clock origin cannot be reconstructed from a stored number after a cold start. A stored wall-clock deadline by itself cannot prove elapsed time under clock rollback or changed origin. The contract needs an original cross-process clock qualification with conservative refusal on ambiguity; absent that, cold write continuation remains denied. It is invalid to silently reinterpret 30 seconds as active CPU time or restart the clock. Expired work cannot be finished by a new write ticket under the current contract.
6. SDK dispatch/outcome state separate from quota state. A durable intent is not proof of dispatch or success. Cold continuation must never repeat the SDK write. It may perform only separately authorized settlement after exact current readback plus complete dual-repository proof; otherwise UNKNOWN and original reservation remain. Old v1/v2 rows have no accounting proof and must not be migrated or topped up.
7. A real terminal receipt that binds final operation/accounting state and exact control revision. Only an original atomic final transaction may clear the reservation. Later legitimate writes in returned A must remain possible without reinterpreting the receipt as a permanent whole-library freeze. B retained-terminal and future publication metadata compatibility need exact original guards.

These are implementation/protocol gaps, not a missing cloud service. The deadline/resource contract does impose a real choice if the intended product behavior requires finishing an expired original operation: that would be a new bounded settlement authorization/resource model for root/user decision, not ordinary restoration of the spent ticket. No such change is proposed as implicitly approved here.

## Smallest useful next work package

Before additional reverse execution, a local design-and-contract slice should enumerate the fixed stages, compute a conservative sufficient envelope from the actual original request/result/finalizer path, and state whether it fits the unchanged whole-task bounds. It must include the protected accounting record's own cost and crash/lease rules. This can proceed with source analysis and small pure synthetic contract checks, without invoking the failed positive, SDK, browser or cloud. If the unchanged bound cannot be established, stop the executable reverse path before native dispatch and retain the held artifact; present a concrete resource/protocol decision once rather than iterating measurements.

Only after that proof is reviewed should runtime implementation own these exact existing areas: `application-generation-selection.js` (private operation/phase owner, durable account and strict cold handling), `idb-repository.js` (original token-scoped preauthorization/charging and exact protected metadata guards), `canonical-generation-publication.js` (fixed preparation reads and accounting inheritance), and the original control-publication owner only if its protected reservation schema must explicitly bind the account. `group-checkpoint-scope.js` may need a narrowly validated terminal receipt classification; it must not allow arbitrary new metadata. New store/body truth, generic issuer, public ready token, permissive rollback RPC and global gate changes are excluded.

Minimum meaningful controls for that future implementation: lost stage-reservation ACK; crash before/after actual SDK with no repeat; A/B split phase; two connections claiming one lease; exact reference/UTF-8-byte exhaustion; late real native completion after observer timeout; clock-origin/rollback ambiguity; old-account-less marker refusal; terminal write failure preserving reservation/UNKNOWN; successful valid terminal receipt then cold open and legitimate A edit. These remain unimplemented/unexecuted, not claimed coverage. Existing v1/IDB owning regressions and shared active-publication checks would be needed at an integration milestone.
